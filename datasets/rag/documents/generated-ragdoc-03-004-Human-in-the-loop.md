# Human-in-the-loop 机制在 Agent 中的应用

## 概念

Human-in-the-loop（HITL）是一种将人类决策与自动化系统相结合的设计理念，在 Agent 系统中表现为关键环节需要人类参与确认或干预。HITL 确保 Agent 在不确定性高、风险敏感或伦理敏感的场景下，不会完全自主执行，而是暂停并等待人类输入。例如，在自动化客服 Agent 中，当用户情绪异常或请求涉及敏感信息时，系统会转接人工。HITL 的核心是平衡自动化效率与人类判断的可靠性。

## 原理

HITL 在 Agent 中的实现基于一个中断-请求-恢复的循环：Agent 在检测到预定义的「触发条件」后，会生成一个状态快照，并构建一个包含上下文、候选动作及其可能影响的人类可读摘要。然后通过异步消息（如 API 回调、消息队列）将请求发送到审批界面。人类审批者可以批准、拒绝或修改动作建议。决策结果返回后，Agent 继续执行或重新规划。整个流程通常由状态机控制，确保超时、降级和回滚策略。

关键技术包括：
- 触发条件定义：基于规则（如置信度阈值）或模型（如不确定性估计）。
- 上下文打包：序列化 Agent 内部状态（当前目标、历史、环境观察）。
- 通信协议：使用 WebSocket 或 REST 接口实现低延迟交互。
- 决策执行：根据人类反馈修改动作序列，可能涉及重规划。

## 实践案例

### 架构流程

考虑一个金融交易辅助 Agent，在自动执行大额订单前需要人类确认。系统架构包含三个主要模块：Agent 执行引擎、HITL 服务、审批前端。

流程如下：
1. Agent 收到交易指令后，评估市场风险。若风险评分超过阈值 0.75，则触发 HITL。
2. Agent 将交易详情（股票代码、数量、价格、风险评估报告）打包为 JSON 请求，发送到 HITL 服务。
3. HITL 服务将请求存入队列，并通过 WebSocket 通知审批前端。
4. 审批者在 30 秒内做出批准、修改或拒绝操作。超时则自动拒绝。
5. 结果通过回调接口返回 Agent，Agent 根据反馈执行或终止。

### 关键参数

- **触发阈值**：风险评分 ≥ 0.75（可配置，0-1）。
- **超时时间**：30 秒（硬上限），超时视为拒绝。
- **审批队列容量**：最多 1000 个待处理请求，超过则降级为自动拒绝。
- **上下文长度**：摘要限制 500 字符，完整报告限制 10KB。

### 异常处理

- **审批者不可达**：重试 3 次，间隔 5 秒；仍失败则转备用审批组。
- **Agent 端超时**：Agent 侧设置 45 秒的超时（比审批超时多 15 秒），超时后执行回滚操作（撤销已部分执行的动作）。
- **数据不一致**：使用版本号（optimistic locking）确保请求与 Agent 状态同步。
- **审批者误操作**：记录审计日志，支持人工事后撤销（需手动干预）。

### 监控指标

- **审批延迟**：P50 < 10 秒，P99 < 25 秒。
- **人为干预率**：占总交易数的 5%-15%，偏离区间报警。
- **超时率**：< 2%。
- **拒绝率**：根据业务场景设定基线（如大宗交易拒绝率 10%）。
- **系统吞吐**：每秒处理 HITL 请求数 >= 50。

### 方案取舍

**优点**：
- 降低自动化误操作风险，尤其在高速交易场景。
- 人类可以注入经验和直觉，处理 Agent 无法量化的因素。

**代价**：
- 延迟增加：每次 HITL 平均增加 15-20 秒执行时间。
- 人力成本：需要配备 24/7 值班审批团队。

**替代方案对比**：
- 完全自主：效率最高但风险大，不适合监管严格行业。
- 事后审计：无实时干预，仅用于追溯，适合低风险场景。
- HITL 与规则混合：将常见模式提前固化规则减少人工干预，但增加维护成本。

综上，HITL 适用于高价值、高风险的 Agent 任务，需根据业务容忍度调整触发参数和审批资源。
