# ReAct循环在Agent中的应用

## 概念

ReAct循环是一种将推理（Reasoning）与行动（Acting）结合的智能体交互模式。它通过交替执行“思考-行动-观察”三步，使Agent能够基于环境反馈动态调整后续策略。该模式借鉴了人类解决问题的认知过程：先分析当前情境（Reasoning），再采取具体操作（Acting），最后根据结果修正理解（Observation）。在大型语言模型驱动的Agent中，ReAct循环常被用于复杂任务分解、工具调用和错误恢复场景，其核心优势在于将语言模型的推理能力与外部环境的执行能力相融合，形成闭环决策系统。

## 原理

ReAct循环的工作原理分为三个连续阶段：

1. **推理阶段（Reasoning）**：Agent接收当前状态与目标，利用大语言模型生成下一步的行动计划或推理链。这包括分析已有信息、识别缺失数据、制定子目标。推理结果通常以自然语言或结构化形式输出，如“我需要查询数据库以获取用户信息”。

2. **行动阶段（Acting）**：Agent根据推理结果执行具体动作。动作可以是调用API、执行代码、发送消息或与用户交互。行动阶段可能触发外部系统变更，如更新数据库状态或获取实时数据。

3. **观察阶段（Observation）**：Agent收集行动后的环境反馈，包括执行结果、错误信息或新状态数据。观察结果被注入下一轮推理，形成循环。例如，API返回错误码“403”会被输入到下一轮推理中，触发重试或切换策略。

循环持续直至达成目标或达到最大迭代次数。ReAct循环的关键在于记忆机制：历史推理链和观察结果需存储在上下文窗口中，以维持连贯的决策轨迹。若采用固定窗口大小，当循环次数过多时需进行摘要或丢弃旧信息。

## 实践案例

### 架构流程

以智能客服Agent处理用户退款请求为例：

1. **输入层**：用户消息“我的订单#12345需要退款”进入Agent。
2. **推理模块**：LLM生成推理：“需要验证订单状态→调用订单查询API→根据结果决定退款流程”。
3. **行动模块**：Agent调用订单查询API，传入订单ID。
4. **观察模块**：API返回“订单已发货，状态：运输中”。
5. **下一轮推理**：LLM根据观察调整计划：“订单运输中无法直接退款→需先联系物流拦截→调用物流拦截API”。
6. **循环**：重复行动与观察，直至退款完结或上报人工。

### 关键参数

1. **最大循环次数**：默认10次，超过则终止并转人工。
2. **上下文窗口长度**：4096 tokens，超出时对历史推理进行压缩摘要。
3. **温度参数**：0.2（低随机性，保证推理稳定性）。
4. **重试次数**：每次行动失败后重试2次，间隔5秒。
5. **超时阈值**：单次行动最大等待时间30秒。

### 异常处理

1. **API调用失败**：捕获网络异常，记录错误日志，重试2次；若仍失败，切换到备用API或标记为“待人工处理”。
2. **推理无限循环**：设置循环次数上限，并监控推理序列的重复度，若连续3次推理内容相似度>90%，触发中断并上报。
3. **上下文溢出**：当token计数接近窗口限制时，自动对最早的两轮推理-行动-观察进行摘要合并，保留关键状态。
4. **非法行动**：行动模块执行前进行合法性校验，如参数格式错误则拒绝执行并反馈错误原因。

### 监控指标

1. **循环成功率**：完整循环后达成目标的占比，目标值>85%。
2. **平均循环次数**：每个任务的平均迭代次数，期望<5次。
3. **平均响应时间**：从输入到最终输出的总延迟，目标<10秒。
4. **重试触发率**：因异常触发重试的比例，警示>5%。
5. **上下文摘要频率**：每分钟触发的摘要次数，过高表示上下文管理需优化。
6. **错误类型分布**：记录API错误、推理错误、超时等分类统计。

### 方案取舍

- **记忆机制选择**：使用滑动窗口摘要 vs 向量检索记忆。滑动窗口实现简单但可能丢失历史细节；向量检索能精准查找但与LLM集成复杂。在任务步骤<20时优先滑动窗口。
- **推理策略**：单步规划 vs 多步规划。单步规划延迟低但全局性弱；多步规划能预先分解步骤但增加首次推理时间。对长流程任务采用多步规划，短任务用单步。
- **行动模块设计**：插件式架构 vs 硬编码函数。插件式可动态扩展但管理成本高；硬编码稳定但不易维护。初期采用硬编码，后期逐步替换为插件。
- **异常回退**：直接转人工 vs 尝试替代方案。直接转人工确保问题解决但降低自动化率；替代方案（如换一种API调用方式）可提升自动化率但可能延长循环。建议对低风险异常尝试替代方案，高风险直接转人工。
