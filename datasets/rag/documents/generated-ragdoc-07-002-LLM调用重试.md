# LLM调用重试策略设计与实现

## 概念

LLM调用重试是指在请求大语言模型（LLM）API时，由于临时性故障（如网络抖动、服务过载、限流等）导致请求失败，系统自动重新发起请求的机制。该机制旨在提高API调用的成功率，保障业务连续性，同时避免因无限重试造成资源浪费或加剧服务负载。

## 原理

重试机制基于幂等性假设：即相同的请求在多次执行后，对系统状态的影响相同。LLM API通常对相同输入返回相同输出（忽略温度参数等随机因素），因此可安全重试。核心原理包括：

1. **重试条件**：仅对可恢复的临时错误进行重试，如HTTP 429（限流）、502（网关错误）、503（服务不可用）、504（网关超时）。永久性错误如400（请求参数错误）、401（认证失败）不应重试。
2. **重试间隔**：采用指数退避（Exponential Backoff）策略，每次重试增加等待时间，避免集中冲击。常见公式为：`等待时间 = 基础间隔 * (2^重试次数) + 随机抖动`。
3. **最大重试次数**：设置上限，防止无限循环。通常为3～5次。
4. **超时设置**：每个请求应设置超时时间，避免长时间阻塞。

## 实践案例

### 架构流程

```
[用户请求] → [重试中间件] → [LLM API]
                        ↑ 失败触发重试
```

重试中间件位于客户端与LLM API之间，拦截失败响应并执行重试逻辑。流程如下：
1. 发起原始请求。
2. 若成功则返回结果。
3. 若失败，检查错误类型是否可重试：
   - 是：计算等待时间，等待后重新请求；重复直至成功或达到最大重试次数。
   - 否：直接返回错误。
4. 若最终失败，抛出异常或返回降级结果。

### 关键参数

| 参数 | 说明 | 推荐值 |
|------|------|--------|
| `max_retries` | 最大重试次数 | 3 |
| `base_delay` | 初始等待时间（秒） | 1.0 |
| `max_delay` | 最大等待时间（秒） | 60.0 |
| `backoff_multiplier` | 指数退避倍数 | 2.0 |
| `jitter` | 随机抖动（秒） | 0.1 |
| `timeout` | 每次请求超时（秒） | 30.0 |

### 异常处理

- **可重试异常**：捕获`HTTPError`中的429、500、502、503、504状态码，以及`ConnectionError`、`Timeout`等网络异常。
- **不可重试异常**：如`HTTPError`中的400、401、403、404等，以及输入校验异常，直接向上抛出。
- **最终失败处理**：若重试耗尽，记录日志，触发告警，并返回友好错误提示或降级响应（如使用缓存结果）。

### 监控指标

| 指标 | 说明 |
|------|------|
| `llm.request.total` | 总请求数 |
| `llm.request.success` | 成功请求数 |
| `llm.request.retry_count` | 重试次数分布（histogram） |
| `llm.request.latency` | 请求延迟（包括重试时间） |
| `llm.request.error_rate` | 最终失败率 |
| `llm.request.retry_trigger_rate` | 触发重试的比率 |

### 方案取舍

- **优点**：显著提升在临时故障下的成功率；无需人工介入；实现简单。
- **缺点**：增加平均延迟；若服务持续不可用，重试会浪费资源并加剧拥堵。
- **替代方案**：
  - **熔断（Circuit Breaker）**：当失败率达到阈值时快速失败，保护下游。
  - **备用API**：切换到其他LLM提供商。
  - **异步重试**：将失败请求放入队列延迟重试，避免阻塞主流程。

**实践建议**：指数退避配合随机抖动，设置合理的重试上限，并监控重试率及最终失败率，动态调整参数。
