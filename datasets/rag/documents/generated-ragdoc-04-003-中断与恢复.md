# LangGraph 中断与恢复机制详解

## 概念

LangGraph 的中断与恢复机制允许在图的执行过程中暂停流程，并在后续恢复执行。中断通常发生在节点之间的过渡点，当满足特定条件时，图会挂起并保存当前状态。恢复操作则从挂起点继续执行，重新加载已保存的状态。这一机制对于处理需要人工介入、等待外部事件或应对错误场景至关重要。

中断点可以配置为图级别的全局设置，也可以在每个节点上单独定义。恢复时，系统会重新执行中断后的所有逻辑，但不会重复已经完成的节点。中断与恢复共同构成了 LangGraph 的持久化运行能力。

## 原理

LangGraph 基于有向图模型，状态在节点间传递。中断机制通过检查点（checkpoint）实现，在每个节点执行后或前，系统可以序列化当前状态并将其存储到持久化后端（如 Redis、SQLite 或内存）。检查点包含图的全局状态、各节点输出以及执行路径。当图被中断时，执行暂停并释放计算资源。

恢复时，代理（runner）从持久化存储中加载最新的检查点，重建图状态，并从中断节点继续执行。为确保一致性，LangGraph 采用“至少一次”语义，即每个节点最多执行一次，但中断点之后的节点至少执行一次。中断条件可以是显式的（如节点返回特定值）或隐式的（如超时、错误）。

关键原理要素：
- 状态序列化：使用 JSON 或 Protocol Buffers 格式确保兼容性。
- 原子提交：检查点写入需原子操作，防止部分写入。
- 幂等性：中断恢复不应产生副作用，节点需设计为幂等。

## 实践案例

### 架构流程

假设我们构建一个客服工单处理图：
1. 输入节点（收单）
2. 分类节点（自动分类）
3. 人工审核节点（需中断，等待人工）
4. 处理节点（执行操作）
5. 通知节点（发送结果）

中断在“人工审核节点”前触发。架构流程如下：
- 启动图，传入工单信息。
- 分类节点自动运行，输出类别。
- 图在“人工审核”节点入口处中断，持久化当前状态（工单ID、类别）。
- 外部系统（如人工客服界面）读取中断列表，展示待处理工单。
- 人工确认或驳回后，调用恢复 API，传入决策结果。
- 恢复执行，从人工审核节点继续，根据决策进入处理或驳回分支。

### 关键参数

- `interrupt_before`: 列表，指定在哪些节点之前中断。例如 `["human_review"]`。
- `checkpointer`: 检查点后端，如 `MemorySaver`, `SqliteSaver`, `RedisSaver`。
- `configurable`: 运行时参数，如 `thread_id` 用于区分不同对话。
- `resume`: 恢复时传入的额外数据，如 `resume_data` 包含人工决策。

### 异常处理

- 检查点写入失败：重试机制，最多重试3次，间隔1秒。
- 恢复时状态不一致：比对输入参数的哈希值，若不一致则标记为脏状态并终止。
- 超时中断：设置全局超时（如30分钟），超时后强制中断并抛出 TimeoutError。
- 重复恢复：引入唯一请求 ID 去重，防止多次处理。

### 监控指标

- `interrupt_count`: 中断频率，监控中断是否合理。
- `resume_latency`: 从中断到恢复的时间，评估人工响应速度。
- `checkpoint_size`: 检查点大小，优化存储。
- `state_repair_rate`: 状态修复率，异常恢复的频率。

### 方案取舍

- **检查点存储方案**：内存（快速但易丢失）、SQLite（嵌入简单）、Redis（分布式持久化）。根据可靠性要求选择。
- **中断粒度**：节点级与步骤级。节点级更简单，但可能丢失部分状态；步骤级更细粒度但开销大。
- **状态完整性**：是否保存完整图状态或仅保存必要字段。完整状态便于调试，但增大存储。
- **恢复策略**：自动恢复 vs 手动恢复。自动恢复适合可预见的错误，手动恢复适合人工审核。
