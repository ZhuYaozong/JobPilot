# 上下文窗口

## 概念

上下文窗口（Context Window）是大型语言模型（LLM）在单次推理中能处理的 token 数量上限。token 是文本的最小单位，可以是单词、子词或字符。窗口大小决定了模型“记忆”范围，直接影响其对长文本的连贯理解、多轮对话的上下文保持以及复杂任务（如文档问答）的准确性。常见的窗口大小有 2048、4096、8192 甚至 128k token。超过窗口的输入会被截断，导致信息丢失。

## 原理

上下文窗口的限制源于 Transformer 架构中的自注意力机制。自注意力的计算复杂度为 O(n²)，其中 n 为序列长度。线性增长的窗口会平方级增加计算成本和显存占用，因此模型训练时会预设最大序列长度。位置编码（如 RoPE、ALiBi）也是基于固定窗口设计的，超出窗口的 token 位置编码不可用，导致模型无法正确理解相对位置。此外，训练数据中的长文本比例也会影响模型对长上下文的适应能力。窗口越大，模型能捕获的长程依赖越强，但训练成本与推理延迟也越高。

## 实践案例

构建一个基于 RAG（检索增强生成）的长文本问答系统，需确保检索到的文档片段拼接后不超出 LLM 上下文窗口。

### 架构流程

1. 用户输入查询。
2. 检索模块：将查询向量化，从向量数据库中召回 Top-K 相关文档块。每个文档块大小预设为 512 token。
3. 上下文组装：按相关性排序，将文档块拼接成提示词，若总长度超过窗口限制，则按关键性裁剪末尾块。
4. 调用 LLM：将提示词送入模型，生成回答。
5. 后处理：若回答被截断，触发重试机制（缩短检索返回数）。

### 关键参数

- model_max_tokens：模型最大上下文窗口，例如 4096。
- chunk_size：文档块大小，设为 512 token。
- top_k：检索返回块数，初始设为 6。
- query_tokens：用户问题占用的 token 数，通常预留 200。
- max_output_tokens：回答最大 token 数，设为 512。
- overlap：分块时的重叠 token，设为 64 以保持边界连贯。

### 异常处理

- 上下文溢出：当检索块总 token 数超过 (model_max_tokens - query_tokens - max_output_tokens) 时，触发裁剪策略：优先保留与查询相关性最高的块；若仍溢出，则进一步减小 top_k。
- 截断回答：若 LLM 输出被截断，检测到截断标记时，自动减少 top_k 重试。
- 检索失败：无相关块时，返回提示“无法从现有文档中找到答案”。

### 监控指标

- 平均上下文使用率：实际输入 token 数占窗口比例，理想值 70%-90%。
- 截断次数：每千次请求中因溢出而裁剪的次数。
- 回答完整率：完整输出（无截断标记）的请求比例。
- 检索命中率：至少一个相关块被使用的请求比例。

### 方案取舍

- 方案 A（短窗口 + 粗检索）：使用 2k 窗口模型，检索块少但成本低。优点是延迟低、算力消耗小；缺点是大文档需多次查询，可能遗漏细节。
- 方案 B（长窗口 + 细检索）：使用 32k 窗口模型，可容纳更多上下文，提升准确率。但成本高 3-5 倍，且长输入下注意力质量可能下降。
- 折中方案（短窗口 + 滑动窗口）：对超长文档分段滑动，每次保留部分历史，适合流式场景。但实现复杂，需管理状态。

实际选型需根据业务场景：对实时性要求高且预算有限选方案 A；对答案质量要求苛刻且允许较高延迟选方案 B；若需连续对话则选用带滑动窗口的方案 A 变体。
