# LangGraph StateGraph建模

## 概念

StateGraph 是 LangGraph 框架中用于构建有状态、多步骤工作流的核心模型。它将应用程序逻辑建模为一张有向图，其中节点代表计算步骤，边代表状态转换。每个节点接收一个状态对象，执行操作后返回更新后的状态。状态对象是一个可序列化的字典或 Pydantic 模型，承载整个工作流的上下文和数据。StateGraph 支持循环、分支和条件跳转，适合构建复杂的 AI 代理、多步推理或自动化流程。

## 原理

StateGraph 的核心原理是状态驱动执行。图由节点和边组成：节点是 Python 函数，签名固定为 `def node(state: State) -> State`；边定义了节点间的连接，可以附加条件路由函数。执行时，引擎从起始节点开始，依次调用节点并传递状态，直到到达终止节点。关键机制包括：
- **State Schema**：定义状态的数据结构，确保类型安全。
- **Reducer**：用于合并来自多个分支的状态更新，常见策略有覆盖、追加或自定义合并。
- **Conditional Edges**：允许根据当前状态值动态选择下一节点，实现分支和循环。
- **State Persistence**：通过 checkpoint 将状态持久化到存储后端（如 SQLite、Redis），支持中断和恢复。

LangGraph 使用 Pregel 算法思想，通过超步（superstep）执行。每个超步处理一组可并行执行的节点，然后同步状态。这使得 StateGraph 既能处理顺序逻辑，也能高效利用并行性。

## 实践案例

### 架构流程

构建一个智能客服工作流，包含意图识别、信息收集、知识检索和最终回答生成。
1. **初始化**：定义状态 schema，包含 `messages`、`intent`、`context`、`answer` 字段。
2. **意图识别节点**：接收用户消息，调用 NLP 模型返回意图标签，更新 `intent`。
3. **信息收集节点**：如果意图需要更多实体，则询问用户并收集；否则跳过。
4. **知识检索节点**：根据意图和上下文查询向量数据库，结果存入 `context`。
5. **生成回答节点**：使用 LLM 生成最终回答，更新 `answer`。
6. **条件边**：根据 `intent` 值路由到不同子图或结束。

### 关键参数

- `max_iterations`: 防止无限循环，默认 10。
- `checkpointer`: 启用持久化，例如 `SqliteSaver`。
- `state_schema`: 使用 `TypedDict` 或 Pydantic `BaseModel`。
- `reducer`: 自定义 `messages` 的追加操作，如 `add_messages`。

### 异常处理

- **节点异常**：在节点函数内捕获异常，将错误信息记录到状态（如 `fields.error`），然后通过条件边进入错误处理节点。
- **超时**：设置节点执行超时，使用 `asyncio.wait_for` 或框架提供的 timeout 参数。
- **状态验证**：在 reducer 中检查状态字段类型，不符合时抛出 `ValidationError`。

### 监控指标

- **节点执行时间**：每个节点的耗时，用于性能分析。
- **状态大小**：每次更新后的状态体积，避免过量数据。
- **图遍历深度**：记录实际经过的节点数，用于检测循环异常。
- **成功率**：成功到达终止节点的比例。

### 方案取舍

- **状态共享 vs 副本**：使用全局可变状态可简化编程，但并发时需加锁；LangGraph 推荐不可变状态更新，通过 reducer 合并。
- **分支 vs 子图**：简单分支用条件边，复杂流程（如多轮对话）提炼为子图，提高复用性。
- **同步 vs 异步**：同步适合简单线性流程；异步节点（`async def`）适合 IO 密集任务，需在图中声明。
- **内存 vs 持久化**：开发阶段内存足够，生产环境必须启用 checkpoint 以支持容错和审计。
