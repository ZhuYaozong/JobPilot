# MCP协议角色与边界

## 概念

MCP（Model Context Protocol）是一种用于定义AI模型与外部系统之间交互边界的协议。它明确了模型中各个组件（如对话管理器、知识检索器、策略执行器等）的角色和职责，确保信息流在可控范围内传递。协议通过标准化接口和权限控制，防止模型越权访问或修改外部资源，同时允许模型在安全边界内获取必要的上下文。

核心角色包括：
- **上下文提供者**：负责向模型提供结构化数据，如用户历史、知识库片段。
- **动作执行者**：在模型决策后执行具体操作，如调用API、更新数据库。
- **监督仲裁者**：验证动作合法性，防止模型产生有害输出。

边界机制通过角色间定义的输入输出规范实现，例如上下文提供者的输出必须符合特定Schema，动作执行者的输入只能来自监督仲裁者过滤后的指令。

## 原理

MCP协议基于分层隔离与令牌传递原理。每一层角色拥有独立的处理空间，通过以下方式维持边界：

1. **接口契约**：每个角色暴露固定接口（如`getContext(request)`、`executeAction(action)`），接口参数和返回值由IDL（接口定义语言）严格描述。任何跨边界的调用必须经过序列化校验，拒绝畸形请求。

2. **权限标签**：模型生成的每个动作都携带权限标签（如`[READ_ONLY]`、`[WRITE]`），监督仲裁者根据标签和当前会话的安全策略决定是否放行。例如，在只读模式中，任何写操作标签的动作都会被拦截。

3. **上下文隔离**：上下文提供者返回的数据只限于模型可见，模型不能直接修改该数据；如需修改，必须通过动作执行者提出的变更请求，经仲裁者审批后才生效。

4. **限流与审计**：每个角色入口记录调用日志，设置频率限制（如每秒最多100次上下文请求），防止模型过度消耗资源。

这些机制共同构建了模型与外部世界之间的“防火墙”，使得AI在明确授权范围内工作。

## 实践案例

### 架构流程

以下案例设计一个智能客服系统，使用MCP协议隔离模型与数据库。

1. 用户提问 -> 模型（对话管理器）接收到上下文提供者注入的用户身份和历史。
2. 模型生成意图和查询请求（例如“查询订单状态”），附带权限标签`[READ]`。
3. 监督仲裁者校验请求：检查用户是否有查询权限（通过令牌验证），并确认动作标签为只读。
4. 动作执行者（订单服务）接收仲裁者放行的指令，查询数据库并返回结果。
5. 结果经仲裁者重新包装后返回模型，模型生成回复。

整个过程中，模型从未直接接触数据库，边界由仲裁者和执行者共同维持。

### 关键参数

- `maxContextTokens`：上下文提供者每次注入的最大令牌数（默认4096）。
- `actionRateLimit`：动作执行者每秒最大处理动作数（默认50）。
- `permissionScope`：当前会话权限范围（可选`read`、`write`、`admin`）。
- `auditLogLevel`：审计日志详细级别（`basic`记录时间、角色；`verbose`记录完整请求体）。

### 异常处理

- **授权失败**：当监督仲裁者发现权限不足时，返回错误代码`ERR_ACCESS_DENIED`，模型需降级处理（如提示用户联系管理员）。
- **上下文超限**：如果模型请求的上下文超过`maxContextTokens`，上下文提供者截断并附加警告。模型可分段请求。
- **动作执行超时**：动作执行者设定10秒超时，超时后返回`ERR_TIMEOUT`，仲裁者通知模型重试或放弃。
- **非法动作**：若模型绕过仲裁者直接调用执行者接口，审计日志标记并阻断，同时触发告警。

### 监控指标

- **边界违例次数**：记录模型或角色尝试越界的行为，用于安全审计。
- **平均仲裁延迟**：仲裁者处理每个请求的平均耗时（目标<5ms）。
- **上下文利用率**：实际使用令牌数/`maxContextTokens`，指导容量规划。
- **动作成功率**：成功执行动作数/总请求数，低于95%需排查异常。

### 方案取舍

**优势**：
- 强化安全性，防止模型误操作或数据泄露。
- 清晰的职责划分便于调试和扩展。

**代价**：
- 增加延迟（每次动作需经过仲裁，延迟增加约2-10ms）。
- 开发复杂度提高，需定义严格的接口和权限模型。

**适用场景**：
- 金融、医疗等高合规领域。
- 对模型行为有严格监管要求的企业级应用。
- 不适合极低延迟（如实时语音）或简单无状态对话。
