# MCP 鉴权与授权机制

## 概念

MCP（Model Context Protocol）中的鉴权（Authentication）与授权（Authorization）是确保客户端、服务器和模型间通信安全的核心机制。鉴权验证通信方的身份，确保请求来自合法的客户端或服务端；授权则控制经过鉴权的实体能访问哪些资源或执行哪些操作。在 MCP 中，通常使用令牌（Token）或证书进行身份验证，并通过声明（Claims）或权限策略实现细粒度授权。

## 原理

MCP 采用基于令牌的鉴权模型。客户端在首次连接时向鉴权服务获取 JWT（JSON Web Token），该令牌包含用户身份、角色和权限声明。每次 MCP 请求（如 execute_operation 或 query_context）都需要在消息头部携带该令牌。服务器收到请求后，首先验证令牌的签名、有效期和签发者，然后解析声明中的权限集合。授权决策基于预定义的策略（Policy），策略是一组规则，定义哪些角色或用户可以对特定资源执行特定动作。常见策略包括 RBAC（基于角色的访问控制）和 ABAC（基于属性的访问控制）。MCP 通过中间件层拦截所有请求，在路由到业务逻辑前完成鉴权和授权。

## 实践案例

### 架构流程

1. 客户端向鉴权服务（Auth Service）发起登录请求，提供用户名/密码或 API Key。
2. Auth Service 验证凭据后，生成 JWT 并返回给客户端，JWT 包含用户 ID、角色列表（如 admin、developer）、过期时间等。
3. 客户端在后续 MCP 请求（如 list_models）的 HTTP Header 中添加 `Authorization: Bearer <token>`。
4. MCP 网关（Gateway）接收请求，调用鉴权中间件提取并验证令牌。
5. 鉴权中间件解析令牌，提取角色，查询策略引擎（Policy Engine）判断该角色是否拥有所需权限。
6. 若验证通过，请求转发至实际服务处理；否则返回 401（未鉴权）或 403（未授权）。
7. 处理完成后，响应带有审计日志记录本次操作。

### 关键参数

- `token_issuer`: 鉴权服务 URL，用于验证签发者。
- `token_valid_duration`: 令牌有效期，默认 3600 秒。
- `allowed_roles`: 允许访问某 MCP 资源的角色列表，如 ["admin", "developer"]。
- `permission_mapping`: 资源操作到所需权限的映射，如 `list_models` 需要 `models:read`。
- `policy_cache_ttl`: 策略缓存时间（秒），减少频繁查询策略引擎。

### 异常处理

| 异常类型 | 处理方式 | 返回码 |
|----------|----------|--------|
| 令牌过期 | 尝试刷新令牌，若失败返回 401 并提示重新鉴权 | 401 |
| 令牌签名无效 | 记录日志，拒绝请求，返回 401 | 401 |
| 权限不足 | 返回 403 并附带缺失权限说明 | 403 |
| 策略引擎不可用 | 降级为缓存策略，若缓存为空则拒绝请求并返回 503 | 503 |
| 令牌缺失 | 返回 401，要求提供有效令牌 | 401 |

### 监控指标

- `auth_request_total`: 鉴权请求总数，标签：result（success/failure）。
- `auth_latency_ms`: 鉴权处理耗时分布。
- `token_expiry_count`: 令牌过期次数。
- `permission_denied_count`: 权限拒绝次数，按资源标签区分。
- `policy_cache_hit_ratio`: 策略缓存命中率。

### 方案取舍

- **对称 vs 非对称签名**：对称签名（HMAC）性能高，但密钥分发困难；非对称签名（RSA/ECDSA）密钥管理更安全，但计算开销略大。选择取决于部署环境的安全等级。
- **本地策略 vs 远程策略引擎**：本地策略查询延迟低，但策略更新需重启；远程策略引擎支持动态更新，但增加网络依赖。建议混合使用：本地缓存 + 远程更新。
- **令牌有效期**：短有效期（如 15 分钟）提高安全性，但增加刷新频率；长有效期（如 24 小时）用户体验好，但被盗风险高。折中采用短有效期 + 无感刷新机制。
- **细粒度权限**：ABAC 更灵活但策略复杂；RBAC 简单易管理但可能不够精细。根据业务复杂度选择，一般前期使用 RBAC，后期演进到 ABAC。
