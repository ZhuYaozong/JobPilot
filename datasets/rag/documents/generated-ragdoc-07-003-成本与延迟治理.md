# AI 推理服务的成本与延迟治理

## 概念

成本与延迟治理是指在 AI 工程化过程中，通过系统化的方法平衡推理服务的经济成本与响应延迟，以在满足业务服务质量要求的前提下实现资源最优配置。随着模型规模扩大和调用量增长，GPU 算力成本与用户感知延迟之间的矛盾日益突出。治理目标包括：降低单位请求的硬件开销，同时将 P99 延迟控制在 Service Level Objective（SLO）以内。

## 原理

成本与延迟的根源在于推理计算与数据传输的时间消耗。治理原理基于以下权衡：
- **计算效率**：通过模型量化（如 FP16 转 INT8）、蒸馏减小模型尺寸，降低每次推理的 FLOPs，从而缩短计算时间并节省 GPU 内存。
- **批处理**：利用 GPU 并行能力，合并多个请求为 batch，提升吞吐量，但会增加单个请求的等待时间，需要找到最优 batch size。
- **缓存**：对重复请求（如常见问题）缓存推理结果，完全消除计算成本，但缓存命中率依赖业务模式。
- **动态资源分配**：根据流量波动自动扩缩容实例，避免闲时浪费。
- **异步与流水线**：将预处理/后处理与推理分离，通过异步调用减少 GPU 空闲等待。

## 实践案例

以某在线翻译服务的推理系统为例，其每日调用量百万级，要求 P99 延迟 < 500 ms，同时控制 GPU 成本在预算内。

### 架构流程

用户请求 → 负载均衡 → 网关（鉴权、限流） → 推理服务池（基于 Kubernetes 部署的 GPU 节点） → 缓存层（Redis） → 模型推理（TensorRT 优化） → 结果返回。推理服务内部：请求先查缓存，命中则直接返回；未命中则进入批处理队列，攒够 batch size 后发送到 GPU 执行。

### 关键参数

- **Batch size**：设为 8（经压测），使 GPU 利用率达到 85% 同时延迟增量小于 100ms。
- **量化类型**：使用 FP16 动态量化，模型体积减小 50%，推理速度提升 1.8 倍。
- **缓存 TTL**：对高频短语设置 10 分钟，整体缓存命中率约 30%。
- **实例数**：基线 4 个 GPU 实例，根据 CPU 负载自动伸缩至 12 个。

### 异常处理

- **超时回退**：若单个请求等待超过 300ms，立即单独推理，避免尾部延迟。
- **降级**：当缓存服务故障时，跳过缓存直接推理，保证可用性。
- **熔断**：连续 5 次请求延迟超过 1s，熔断该区域实例，流量切至备用可用区。

### 监控指标

- **延迟**：P50 120ms，P99 350ms，P999 800ms。
- **吞吐量**：平均 1200 QPS，峰值 3000 QPS。
- **成本**：每百万请求的 GPU 费用从 $120 降至 $80。
- **其他**：GPU 利用率、批处理队列长度、缓存命中率。

### 方案取舍

- **延迟优先**：若业务对实时性要求极高，可关闭批处理、扩大缓存、增加实例数，但成本上升。
- **成本优先**：接受稍高延迟（P99 600ms），增大 batch size 至 16，量化至 INT8，减少实例基线至 2 个。
- **平衡方案**：采用自适应批处理，根据当前负载动态调整 batch size，实现成本与延迟的折中。最终采用平衡方案，在满足 SLO 的前提下成本最优。
